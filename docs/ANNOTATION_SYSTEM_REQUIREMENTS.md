## 1. 状态标记与维护规则

- `[已完成]`：代码已实现，并且有对应测试或实际验收证据。
- `[已实现/待验收]`：代码已提交或已能运行，但尚未完成充分测试。
- `[部分完成]`：已有部分实现，仍有明确缺项或已知缺陷。
- `[未完成]`：需求已确定，尚未实现。
- `[暂缓]`：明确不在当前开发阶段处理。

维护要求：

1. 每次开发开始前，先阅读本文件和当前分支最新代码。
2. 新增需求时，先登记需求编号、描述、优先级和状态，再开发。
3. 需求发生变化时，更新原条目，不保留相互矛盾的旧描述；在版本记录中说明变化。
4. 功能完成后，只有在构建、自动化测试或用户实际验收达到对应要求后，才能将状态改为“已完成”。仅提交代码不能视为已验收。
5. 每次交接时更新“当前进度”“已知问题”“下一步”，并记录最新提交。
6. 不得为了实现一种批注而将三种批注合并成同一种实体，也不得擅自修改已经正常工作的阅读器功能。

### 1.1 新功能的整体架构文档要求（强制）

本项目不能只记录“增加了某按钮/某功能”或“代码已完成”。每次开发新功能、扩展现有功能或改变跨模块行为，都必须把**整体开发框架和设计思路**同步写入本需求文档，保证新对话或新开发者不依赖聊天记录也能理解原有方案。

每项中型及以上功能，至少记录以下内容；简单局部修复可按实际情况精简，但必须说明它属于哪个既有模块、调用哪个既有接口：

1. **目标与边界：**要解决什么问题、用户如何使用、包含什么、不包含什么。
2. **现有架构与复用关系：**改动前的模块结构、所在层、已有服务/接口，以及为什么复用它们；明确禁止另起一套重复系统的部分。
3. **整体模块划分：**各层/各类/各组件的职责、所有权、依赖方向和关键代码文件。
4. **核心数据模型：**数据实体、字段含义、持久化位置、主外键/关联关系、生命周期；若不改变数据结构，也要明确写出沿用什么结构、为什么不改。
5. **关键数据流与调用流程：**从用户操作入口开始，经过哪些 UI、控制器/引擎、服务、Repository/数据库或渲染层，最后如何反馈到界面；必要时用时序图或流程图。
6. **接口与坐标/状态契约：**跨层参数、返回值、索引/坐标语义、事件、线程要求、资源释放规则，以及与现有模块的契约。
7. **交互和状态管理：**入口、成功/失败、加载/空状态、编辑/只读、取消、项目切换、异步重入等行为。
8. **性能、兼容和安全约束：**大文件内存策略、缓存边界、数据库迁移、旧项目兼容、并发/线程、错误恢复等。
9. **设计决策与非目标：**重要方案选择、未选方案及原因、暂缓项、不得破坏的既有行为。
10. **测试和验收：**自动化测试覆盖什么、构建命令、用户冒烟测试路径、已知缺口，以及“代码已实现/自动化测试通过/用户已验收”的分别状态。

执行流程：

- **开发前：**先检查当前分支最新代码和本文档，梳理现有调用链；先把拟采用的架构、模块职责、数据流和数据契约写入本文档，再开始实现。涉及数据模型、核心接口、跨模块依赖或整体交互方式的变更，必须先与用户讨论确认。
- **开发中：**若实际实现与原设计不同，立即修正文档，不保留已经失效的架构描述。
- **开发后：**同步更新实际代码位置、真实调用流程、数据结构、状态、测试结果、用户验收情况、已知问题和后续步骤；在版本记录中记录提交 SHA。
- **文档组织：**复杂功能可以另建 `docs/<feature>-architecture.md` 记录详细设计，但本需求文档必须保留该功能的架构摘要、关键约束、状态和详细文档链接。不能只把架构放在聊天记录、交接提示词或独立文档而不在需求文档中建立入口。
- **交接前：**确认需求文档中的当前架构与最新代码一致，清理已过时的“待验收/未实现”描述，保留历史记录但明确标为历史状态。交接提示词必须以需求文档为准并指出最新分支、HEAD、功能提交和下一步。

## 2. 产品目标与总体原则

Fujiy Notepad 是面向长篇 TXT 小说阅读、剧情分析、人物研究和写作素材积累的 Windows 桌面软件。

### 2.1 三种独立批注

软件需要支持三种相互独立的批注实体：

| 类型 | 绑定对象 | 主要用途 | 当前状态 |
|---|---|---|---|
| 小批注 | 原文中的一个或多个文本片段 | 零散记录、素材提取、剧情细节、人物表现 | [主体功能已实现]；章节级锚点升级已通过用户冒烟测试；BUG-012 按用户要求暂缓；完整回归暂缓至最终阶段 |
| 章节批注 | 一个具体章节；同一章节允许多条 | 单章概括、点评和分析 | [主体功能已实现]；章节目录及右侧新建/阅读器右键两种入口已由用户实测通过；完整 CRUD、组合筛选、重识别等 UI 流程仍待最终验收 |
| 大批注 | 连续的多个具体章节 | 阶段剧情总结、人物成长线、势力变化、伏笔整理 | [主体功能已实现]；用户已完成基本功能测试并确认通过；整体视觉统一和完整回归待后续 |

三种批注必须保持独立：

- 各自拥有独立的数据实体、正文、分类和管理界面。
- 小批注被用作大批注写作参考时，不自动建立两者之间的绑定关系。
- 章节批注不会自动成为大批注的子项。
- 修改或删除一种批注，不得改变另外两种批注已经保存的内容。
- 大批注工作区左侧显示的小批注和章节批注只是参考资料，不是大批注的子批注。

建议分别管理小批注、原文锚点、章节批注、大批注、大批注章节关联；章节索引供三种批注查询和跳转使用。不要把三种批注全部塞进一张表再用类型字段区分。

### 2.2 阅读器与项目原则

- [已完成] 支持 TXT 小说阅读和大文件按需读取。
- [已完成] 支持行索引、搜索、定位、书签等基础阅读功能。
- [已完成] 小说项目独立管理，项目数据保存在各自项目目录和 SQLite 数据库中。
- [部分完成] 原文工作副本、带标记副本导出和标记完整性校验已实现；差异预览、变更应用及恢复流程尚未实现。
- [已完成] 批注数据不得写入或污染原始小说 TXT 正文。
- [已完成] 阅读器不能因批注功能而一次性加载整本长篇小说。
- [暂缓] 软件启动主界面改为项目列表模式；本阶段不得顺手修改启动和关闭项目的主界面流程。

章节级锚点恢复的优先顺序：

1. **章节正文指纹未变化**：按稳定 ChapterId 和 LF 归一化后的章节内相对偏移恢复当前文件位置，兼容 CRLF/LF 宽度差异；标题行长度变化时，正文锚点按新旧 BodyStartOffset 的归一化相对差值平移，校验摘录后更新全文偏移和文档版本。
2. **章节标题变化但正文指纹未变化**：锚点相对偏移以章节范围起点（标题行起点）为基准；正文锚点按新旧 BodyStartOffset 的差值平移，标题行内锚点单独校验，不得因标题长度变化错位。章节范围包含标题行，BodyStartOffset 指标题行及其换行符之后的正文起点；正文 SHA-256 不包含标题行。
3. **章节正文指纹变化**：只在该锚点所属章节范围内查找；若同章出现多次，再用前后文上下文和原相对位置消歧。同一 Annotation 的其他章节锚点独立处理。
4. **章节身份已删除或无法可靠匹配**：不搜索其他章节来“碰运气”，保留批注并提示人工重新关联。
5. **旧版锚点没有 ChapterId**：允许一次全书唯一匹配作为兼容迁移；匹配成功且章节索引可信后，补齐 ChapterId 和新锚点元数据。

**锚点边界约束：** 对每个非孤儿锚点，必须满足 Chapter.StartOffset <= Anchor.StartOffset < Anchor.EndOffset <= Chapter.EndOffset，并且其起止范围只命中一个活动章节。创建、追加、导入、编辑和数据库写入均需执行该校验；跨章选择不能以一个连续锚点入库。

章节目录应使用虚拟化列表承载大量章节，不应把上千个章节全部转换为永久 UI 容器。章节批注筛选和新建窗口后续应复用目录的搜索/选择能力，避免各自维护不同的章节列表实现。

## 12. 阅读器比例字体渲染引擎改造

### 12.1 已确认的技术方向

- 阅读器必须支持普通中文比例字体，包括系统已安装的中文字体和中英文混排字体。
- 保留现有大文件按需读取架构、LineProvider、LineIndexer、字节源及有界缓存，不使用 RichTextBox 或全文加载方案替换阅读器。
- 保留 Win2D/DirectWrite 作为绘制和文字排版基础，逐步替换固定字符宽度计算。
- 保留 DocumentTextOffsetMap 和现有批注锚点数据结构；批注坐标继续使用全文 UTF-16 偏移。
- 字体、字号、行距、正文宽度和窗口大小只影响临时布局，不得修改原文偏移或 SQLite 批注锚点。

### 12.2 坐标约定

必须区分文件字节偏移、原文 UTF-16 偏移和布局/屏幕坐标：

1. 文件字节偏移仅服务于文件读取和索引。
2. 原文 UTF-16 偏移是章节、批注和文档定位的持久化坐标。
3. 布局坐标和屏幕像素只用于当前渲染，不得持久化为批注位置。

所有布局接口返回的字符索引必须是原始逻辑行字符串中的 UTF-16 偏移。内部即使进行 Tab 展开或其他视觉投影，也必须在布局后端内部完成反向映射，不能把显示字符串索引暴露给上层。

### 12.3 新布局接口

Phase 1 新增 Presentation 层 UI 无关契约：

- TextLayoutOptions：字体、字号、最大宽度、自动换行、行距倍数和 Tab 宽度。
- ITextLayoutProvider：为一条原文逻辑行创建布局。
- ITextLayoutResult：提供视觉行、光标几何、鼠标命中、原文范围矩形和前后有效光标位置。
- TextLayoutVisualLine：以半开区间表示视觉行对应的原文 UTF-16 范围。
- TextLayoutHitTestResult：返回原文字符/字形簇的 UTF-16 起点和长度，兼容代理对及多 UTF-16 单元字符。
- TextCaretGeometry / TextLayoutRect：表达布局局部坐标中的光标和范围几何。

Phase 2 已在 WinUI 层新增 Win2DTextLayoutProvider / Win2DTextLayoutResult，基于 CanvasTextLayout 实现字体测量、真实字形换行、视觉行指标、鼠标命中、光标位置和范围矩形。Presentation 仍不引用 WinUI、Win2D 或 WinRT 类型。布局结果负责释放原生布局和字体格式资源，并要求在 UI 线程创建、查询和释放。

### 12.4 旧实现迁移规则

- LineColumns、LineWrapper 和当前 TextLayoutEngine 属于旧固定字符单元布局路径。
- Phase 1 只新增接口、坐标契约、测试和文档，不改变现有阅读器绘制行为；用户已完成 Release x64 编译和 501 项 Presentation 测试验收。
- Phase 2 已实现并经用户验收的 Win2D/DirectWrite 后端，随后已接入 Phase 3。
- Phase 3 已将比例布局路径接入 TextLayoutEngine/TextCanvas，旧固定字符单元路径仍保留为回退；代码集成不等于端到端运行验收通过。
- 在新旧路径功能等价前，不删除旧实现，也不修改批注核心逻辑。

### 12.5 大文件性能要求

- 只为当前可视逻辑行及少量相邻行创建布局对象。
- 布局缓存必须有界，滚动离开视口后释放不再需要的原生布局对象。
- 缓存身份必须包含原文行身份/版本、字体、字号、可用宽度、换行模式、行距和 Tab 设置。
- 字体或窗口变化时按需重排可视区域，不扫描并排版整本小说。
- 保留当前 LineProvider 单行 64KB 上限；超长无换行文本的分块布局另行设计，不在本阶段扩大限制。

### 13.9 Phase 4：全局阅读设置与主界面视觉隔离（4.1 已验收，4.2 代码待测试）

**核心决定：阅读界面与软件主界面是两套独立视觉系统。** 本阶段只开发阅读器专用设置；主界面菜单、工具栏、状态栏、批注面板、批注弹窗等保持固定样式，不增加字体、字号、背景、文字颜色设置，也不把阅读主题传递给这些控件。

#### 13.9.1 全局数据模型与保存位置

- 阅读设置对所有小说项目统一生效，不按项目分别保存。
- 保存到现有用户级 `%LOCALAPPDATA%\\FujiyNotepad\\settings.json`，不写入项目 `project.json`，不新增或修改 SQLite 表。
- 在 `FujiyNotepad.Presentation/AppSettings.cs` 中增加嵌套 `ReaderSettings Reader` 对象；具体字段：
  - `FontFamily`：系统安装字体名称，初始默认 `Microsoft YaHei`。
  - `FontSizeDip`：字号，DIP，初始默认 18。
  - `LineSpacingMultiplier`：自然行距倍数，初始默认 1.4。
  - `ContentWidthDip`：正文最大宽度，DIP，初始默认 900；0 表示自适应可用宽度。
  - `Theme`：阅读器主题，初始默认 `Paper`；第一版支持 `Paper`、`Warm`、`Night`，不提供 `FollowApp`。
- `AppSettings.Theme` 继续属于原应用外观设置；阅读主题不得读取或修改它。
- 现有顶层 `AppSettings.FontFamily`、`FontSize` 是原文本视图设置的兼容字段，不是主界面字体设置。旧 JSON 缺少嵌套 `Reader` 时，将这两个旧值迁移到 `ReaderSettings`；迁移后阅读器和字体/Zoom 快捷操作只读写 `AppSettings.Reader`。主界面控件不得使用这些值。
- `SettingsStore.Load` 负责旧 JSON 兼容和参数归一化：空字体、无效主题、非有限/越界字号、行距和宽度均回退到安全默认值；继续使用现有源生成 JSON 序列化。

#### 13.9.2 渲染与布局职责

- 已新增独立 `ReaderPalette`，不要把阅读主题混入现有应用主题解析流程。
- ReaderPalette 覆盖阅读背景、正文、光标、选区、搜索高亮、选中词高亮、标记刻度、书签、空白字符、控制字符及小批注标记颜色。
- `TextCanvas` 只消费阅读器设置和 ReaderPalette。修改 Reader.Theme 不得修改 `RootGrid.RequestedTheme`，也不得改变菜单、批注面板或弹窗；当前代码已移除对 `ActualThemeChanged` 的阅读配色依赖。
- Windows 高对比度是唯一可以覆盖所选阅读主题的系统级无障碍覆盖。
- 复用已有 `TextLayoutOptions` 和 Win2D/DirectWrite 提供器；将 Reader.FontFamily、FontSizeDip、LineSpacingMultiplier 传递到现有比例布局链路，不创建第二套布局引擎。
- 正文宽度使用“全宽阅读视口/背景容器 + 居中最大宽度正文容器”。标记刻度与正文容器对齐，视口两侧保持同一阅读背景。
- 修改排版时只清理受影响的可视区/邻近区布局缓存，尽量保存当前可见原文 UTF-16 位置并恢复；不全文加载、不全书同步重排。
- 所有字体/字号/行距/宽度/颜色均为临时显示属性，不修改全文 UTF-16 偏移、ChapterId、批注锚点或 SQLite 数据。

#### 13.9.3 设置界面与行为

- 在 View 菜单提供统一“阅读设置”入口。
- 设置窗口编辑临时快照；“应用”后即时更新当前阅读器并保存全局设置；“取消”丢弃临时更改。
- 现有字体选择和 Zoom 快捷操作如保留，必须操作同一 ReaderSettings 模型，不得另存一套字体/字号状态。
- 第一版支持系统安装字体选择、字号、行距、正文最大宽度/自适应宽度、Paper/Warm/Night 三种预设主题；不做自定义 RGB、字体文件导入和每项目覆盖。
- 切换小说项目不改变阅读设置；重启软件后恢复同一套全局阅读设置。
