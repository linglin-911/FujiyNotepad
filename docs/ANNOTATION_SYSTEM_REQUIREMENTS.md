## 1. 状态标记与维护规则

- `[已完成]`：代码已实现，并且有对应测试或实际验收证据。
- `[已实现/待验收]`：代码已提交或已能运行，但尚未完成充分测试。
- `[部分完成]`：已有部分实现，仍有明确缺项或已知缺陷。
- `[未完成]`：需求已确定，尚未实现。
- `[暂缓]`：明确不在当前开发阶段处理。

维护要求：

1. 每次开发开始前，先阅读本文件和当前分支最新代码。
2. 新增需求时，先登记需求编号、描述、优先级和状态，再开发。
3. 需求发生变化时，更新原条目，不保留相互矛盾的旧描述；在版本记录中说明变化。
4. 功能完成后，只有在构建、自动化测试或用户实际验收达到对应要求后，才能将状态改为“已完成”。仅提交代码不能视为已验收。
5. 每次交接时更新“当前进度”“已知问题”“下一步”，并记录最新提交。
6. 不得为了实现一种批注而将三种批注合并成同一种实体，也不得擅自修改已经正常工作的阅读器功能。

## 2. 产品目标与总体原则

Fujiy Notepad 是面向长篇 TXT 小说阅读、剧情分析、人物研究和写作素材积累的 Windows 桌面软件。

### 2.1 三种独立批注

软件需要支持三种相互独立的批注实体：

| 类型 | 绑定对象 | 主要用途 | 当前状态 |
|---|---|---|---|
| 小批注 | 原文中的一个或多个文本片段 | 零散记录、素材提取、剧情细节、人物表现 | [部分完成]；原文修改后的唯一摘录自动修复已加入，待本次实测 |
| 章节批注 | 一个具体章节；同一章节允许多条 | 单章概括、点评和分析 | [部分完成]；主要功能已实现，但章节筛选显示和新建弹窗仍有 UI 缺陷待修复 |
| 大批注 | 连续的多个具体章节 | 阶段剧情总结、人物成长线、势力变化、伏笔整理 | [未完成] |

三种批注必须保持独立：

- 各自拥有独立的数据实体、正文、分类和管理界面。
- 小批注被用作大批注写作参考时，不自动建立两者之间的绑定关系。
- 章节批注不会自动成为大批注的子项。
- 修改或删除一种批注，不得改变另外两种批注已经保存的内容。
- 大批注工作区左侧显示的小批注和章节批注只是参考资料，不是大批注的子批注。

建议分别管理小批注、原文锚点、章节批注、大批注、大批注章节关联；章节索引供三种批注查询和跳转使用。不要把三种批注全部塞进一张表再用类型字段区分。

### 2.2 阅读器与项目原则

- [已完成] 支持 TXT 小说阅读和大文件按需读取。
- [已完成] 支持行索引、搜索、定位、书签等基础阅读功能。
- [已完成] 小说项目独立管理，项目数据保存在各自项目目录和 SQLite 数据库中。
- [已完成] 原文工作副本及修改校验相关基础功能已存在。
- [已完成] 批注数据不得写入或污染原始小说 TXT 正文。
- [已完成] 阅读器不能因批注功能而一次性加载整本长篇小说。
- [暂缓] 软件启动主界面改为项目列表模式；本阶段不得顺手修改启动和关闭项目的主界面流程。

章节级锚点恢复的优先顺序：

1. **章节正文指纹未变化**：按稳定 ChapterId 和章节内相对偏移恢复全文位置，校验摘录后更新全文偏移和文档版本。
2. **章节标题变化但正文指纹未变化**：锚点相对偏移以章节范围起点（标题行起点）为基准；正文锚点按新旧 BodyStartOffset 的差值平移，标题行内锚点单独校验，不得因标题长度变化错位。章节范围包含标题行，BodyStartOffset 指标题行及其换行符之后的正文起点；正文 SHA-256 不包含标题行。
3. **章节正文指纹变化**：只在该锚点所属章节范围内查找；若同章出现多次，再用前后文上下文和原相对位置消歧。同一 Annotation 的其他章节锚点独立处理。
4. **章节身份已删除或无法可靠匹配**：不搜索其他章节来“碰运气”，保留批注并提示人工重新关联。
5. **旧版锚点没有 ChapterId**：允许一次全书唯一匹配作为兼容迁移；匹配成功且章节索引可信后，补齐 ChapterId 和新锚点元数据。

**锚点边界约束：** 对每个非孤儿锚点，必须满足 Chapter.StartOffset <= Anchor.StartOffset < Anchor.EndOffset <= Chapter.EndOffset，并且其起止范围只命中一个活动章节。创建、追加、导入、编辑和数据库写入均需执行该校验；跨章选择不能以一个连续锚点入库。

章节目录应使用虚拟化列表承载大量章节，不应把上千个章节全部转换为永久 UI 容器。章节批注筛选和新建窗口后续应复用目录的搜索/选择能力，避免各自维护不同的章节列表实现。

## 9. 开发、构建与测试约定

### 9.1 分支与平台

- 分支：`feature/novel-project-annotations`
- Windows x64 开发和验收命令统一显式添加 `-p:Platform=x64`。
- 当前解决方案默认平台仍可能选择 ARM64；不得因为配置文件中 x64 排在前面就假定默认构建是 x64。
- 除非后续经过实测修复并确认默认平台，否则所有构建/测试/运行命令都保留显式 x64 参数。

### 9.2 常用命令

```powershell
git pull --ff-only origin feature/novel-project-annotations

dotnet restore src/FujiyNotepad.slnx -p:Platform=x64

dotnet build src/FujiyNotepad.slnx --configuration Release --no-restore -p:Platform=x64

dotnet test src/FujiyNotepad.slnx --configuration Release --no-build --verbosity normal -p:Platform=x64

dotnet build src/FujiyNotepad.slnx --configuration Debug -p:Platform=x64

dotnet run --project src/FujiyNotepad.WinUI/FujiyNotepad.WinUI.csproj --configuration Debug -p:Platform=x64
```

### 9.3 代码与测试要求

1. 先检查最新代码、架构和调用关系，再修改。
2. 优先复用现有 SQLite、DocumentTextOffsetMap、TextCanvas 和 TextLayoutEngine，不重复建表或另起一套系统。
3. 新增 UI 功能时同步处理加载状态、空状态、异常、异步重入和项目切换。
4. 任何按可视区域加载的锚点/标记都必须避免每次滚动重复执行昂贵的全文查询。
5. 阅读器绘制必须使用真实文本布局坐标，不能依赖固定字符宽度猜测文本位置。
6. 重叠和嵌套原文锚点是合法数据，绘制和点击逻辑必须支持。
7. 每个独立功能完成后执行对应单元测试和 x64 构建。
8. 用户验收后更新状态和版本记录。
